# Working in the FEP repo

This project has a small number of ways to waste an hour, and they are all
invisible until you hit them. Every rule below exists because it already went
wrong once.

For FEP *content* -- newsletters, standings, superlatives, the algorithm's
meaning -- use the `fep-master` skill instead. This skill is only about the
code and the repo.

## The source of truth

`~/FEP Data Center/2026/`, on branch `main`. That is the whole project.

There is one branch and one working tree, deliberately. In September 2026 this
repo had a second checkout (`fep-dashboard-redesign/`) sitting on a branch that
had diverged 28 commits earlier. Each side had half the project: one had the
dashboard everyone wanted, the other had the CMS pipeline that publishes it.
Nobody could tell which was canonical, and the answer turned out to be
"neither". Recovering that cost a merge, a trial worktree and a full re-verify.

So before starting work:

```bash
git -C "$HOME/FEP Data Center/2026" worktree list   # expect exactly one line
git branch                                          # expect only main
git status --short                                  # expect clean
```

If any of those surprises you, resolve it before writing code. A second
worktree or branch is not a workspace, it is an unmerged fork waiting to
happen.

**Check for a second session too.** More than one agent has edited this repo at
the same time. If `git status` shows changes you did not make, stop and ask
rather than committing them -- you cannot tell finished work from work in
progress by looking at a diff.

## What is generated, and what you actually edit

| You edit | It generates | Never edit the generated one |
|---|---|---|
| `dashboard/template.html` | `dashboard/index.html` | it is gitignored and overwritten on every build |
| the season file + model | `newsletters/week-NN/` | regenerated by `cli.py week` |
| the season file + model | `chart-data/2026/week-NN.json` | published per week, immutable once written |
| `fep/cms.py` | `exports/cms/` | gitignored, regenerate with `cli.py cms --csv` |

`index.html` is 100+ KB of built output with the week's data baked into a
`<script type="application/json">` block. Editing it looks like it works and is
erased by the next build.

**The dashboard is one page in two modes, and the mode is not a setting.** It
is decided by whether anything is behind it.

Served by `dashboard/serve.py` (the `scripts/FEP.app` icon) it is the
application: the page is rendered from the season file on every load, and the
buttons run the weekly run, the ESPN refresh, the Sheet push, the CMS tables, a
pick-sheet load and the git commit. Opened as a file it is a viewer, because a
`file://` page has no origin and can reach nothing, and every button falls back
to copying the command that would do the thing.

Two rules survive that and are worth defending:

- **The server implements nothing.** Every action is a call into `cli.py` with
  its output captured, so there is still exactly one weekly run and a button
  cannot drift away from the command it replaces. A new button means a new
  `cli.py` command first.
- **The page still persists nothing of its own.** The What If tab is
  deliberately ephemeral, and the only thing kept across a reload is which tab
  you were on, in the URL hash. If someone asks to make the dashboard "save"
  something, the answer is still that the *run* should save it into the season
  file.

**The payload is cached, and the cache key covers the code.** `collect()` is
about eleven seconds, nearly all of it counterfactual boards, so `serve.py`
caches it in `data/dashboard_cache/` against a fingerprint of the season file,
`build.py`, `fep/*.py` and `data/history/`. If you edit the model and the
dashboard shows the old numbers, the fingerprint is what to look at first --
but it is meant to cover exactly that case, so suspect a real bug before
blaming it. Never write that cache from a test: `tests/test_serve.py` has a
`CacheIsolated` base class for anything that touches `_payload()`, and it
exists because a stub leaked into the real cache once and the server then
served a one-key payload and died on it.

`serve.py` is also the only surface in this repo that takes input from outside
the process, and one of its actions writes to a real Google Sheet. It binds
`127.0.0.1` only, every action requires a token minted at launch and given to
the page it rendered, and the writes that leave this machine arm on the first
press and fire on the second. `tests/test_serve.py` holds that boundary. Do not
relax any of it to make something convenient.

## The one irreplaceable file

`data/season_2026.json` holds the picks, results, weights, scores and one
frozen snapshot per week. Everything else in the repo can be rebuilt from it
and from ESPN. It cannot be rebuilt from anything.

Two properties worth preserving:

- **Facts are stored, statistics are not.** Leverage, heat check and
  differentiation are recomputed on demand, because a cached statistic can
  silently disagree with the board after a result is corrected. Do not add a
  computed number to the season file.
- **Snapshots freeze.** A week's snapshot is what the family read that week.
  Changing the engine in 2029 must not move a number published in 2026. The CMS
  tables depend on this and `tests/test_cms.py` asserts it.

Every result, score and weight records whether it came from ESPN or from a
human. `refresh` never overwrites a manual override, so it is always safe.

## The repo is self-contained, and that was expensive

Everything the code reads lives inside the repo:

- `data/history/` -- the ten-season record, six CSVs
- `tests/fixtures/simulator_2025.py` -- the frozen 2025 regression baseline
- `data/season_2026.json` -- this season

None of that was true until it was fixed. History was read from the
`fep-master` skill's data folder down a path containing two session UUIDs, the
2024 and 2025 picks were parsed out of Jacob's old simulator scripts as source
text, and the most important test in the suite executed a file in a sibling
year folder. A checkout anywhere else lost four seasons and reported it as
**the record book disagreeing with itself** -- which reads like data corruption
and sends you looking in entirely the wrong place.

So: **if you find yourself writing a path containing `..` or `~/Library`, that
is the bug.** `FEP_DATA_DIR` exists to point history somewhere else
deliberately; nothing else should reach outside.

The check that this still holds is to run the suite from a copy with no
siblings:

```bash
rsync -a --exclude .git --exclude __pycache__ "$HOME/FEP Data Center/2026/" /tmp/iso/2026/
cd /tmp/iso/2026 && python3 tests/test_engine.py
```

Anything that fails there is something that escaped the repo.

## Verifying a change

There are four test files, not one, and 191 tests between them. `test_engine.py`
alone is the one people run and it misses two thirds of the suite:

```bash
cd "$HOME/FEP Data Center/2026"
for t in test_engine test_review_fixes test_cms test_backfill; do
  printf "%-20s " "$t"; python3 tests/$t.py 2>&1 | tail -3 | tr '\n' ' '; echo
done
```

The ones worth understanding when they fail:

- **the 2025 replay** must match the published boards exactly, or ten years of
  family history quietly changes
- **the retro replay** must reproduce the right champion and exact winning score
  for all ten seasons
- **the CMS immutability check** replays a season and compares every frozen row
  against its first published version
- **no em dashes or en dashes** anywhere in the stat pack -- this is a real
  assertion, so write `--` in generated prose

For anything touching the dashboard, tests are not enough. Build it and look at
it, at desktop width and at 375px:

```bash
python3 cli.py dashboard && open dashboard/index.html
```

A payload that passes every test can still render a blank tab or a table that
pushes the page sideways.

## Pushing to GitHub

The remote is `jleibowitz9/fep`, a personal repo. This machine's active `gh`
account is the *work* one, so a plain `git push` authenticates as
`jacobleibowitz-forage` and is refused with a 403. Commits are attributed
correctly the whole time -- only the transport is wrong, which is why this went
unnoticed for a season's worth of commits.

The repo is configured with the account in the remote URL. To push:

```bash
"$HOME/FEP Data Center/2026/scripts/fep-push.command"
```

or, equivalently, supply the personal token for the one command:

```bash
GH_TOKEN="$(gh auth token --user jleibowitz9)" git push origin main
```

Do not fix this by running `gh auth switch` -- that changes the global account
and breaks work repos. Do not write the token into the keychain or into a file.

The weekly run pushes on its own, so in normal operation this is already
handled. See the `fep-week` skill.

## Things that will bite you

- **`credentials/` is gitignored and must stay that way.** It holds the Apps
  Script deployment URL and tokens. There is no service-account key and there
  cannot be one: key creation is blocked on this account by an org policy, which
  is why the CMS push goes through an Apps Script web app instead. One
  deployment, named by `cms_url`.
- **The CMS tables are the only thing written to a spreadsheet.** A second
  writer put weekly percentages into `B2:M20` of `Weighted - MASTER`; it was
  retired in September 2026 once nothing read that tab. The guards that remain
  -- tab allowlist, header match, season boundary, frozen rows -- exist in both
  the Python client and the Apps Script, because a guard that only exists on
  the caller is not a guard. Do not relax either one.
- **CMS columns are appended, never inserted.** Framer maps sheet columns to CMS
  fields; inserting one shifts every column after it and a field silently starts
  showing its neighbour's values.
- **Only the standard library**, on system Python 3.9. `requirements.txt` is now
  empty of packages -- the last two went with the service-account transport. Do
  not add a dependency to solve something small.

## Commit style

Match the repo. Subjects are sentences that say what changed, not conventional-
commit prefixes: *"A competitor's colour is an identity, not a list index"*,
*"Refuse to push against a stale deployment"*, *"The formula guard rejected
every away game"*.

Bodies explain **why**, and say what was verified. The repo's history is
genuinely readable and is worth keeping that way.

Commit only your own paths. If another session's work is sitting in the tree,
`git add` the specific files you touched rather than `-A`.
